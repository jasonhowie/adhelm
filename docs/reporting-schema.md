# Reporting and recommendation schema

Last updated: 2026-09-04

## Principles

The product normalizes enough structure to compare and operate campaigns while
preserving provider truth. It must never erase differing attribution models,
windows, currencies, timezones, freshness, privacy thresholds, or provider-
specific semantics to manufacture one authoritative number.

Raw provider responses are validated in memory and are never persisted by
default. Only allowlisted normalized records enter local history.

Canonical persisted history is append-only JSONL; CSV and JSON reports are
deterministic projections, not independently written stores. Write operations
always use the change ledger. Explicit report/sync and creative-analysis runs
append normalized observations by default, with an explicit ephemeral-read
option. See [`local-ledger-and-exports.md`](local-ledger-and-exports.md).

## Report envelope and hierarchical performance rows

The primary consumer of structured reports is the customer's agent. Reports
feed compact summaries and user-selected documents, spreadsheets, or HTML
artifacts. The output policy controls purpose, timing, format, destination, and
detail; optional presentation files are not generated by default.
Agent-visible output follows the allowlisted/redacted sharing boundary by
default, with bounded pagination or local artifact references. The agent may
send observed output to its configured model; local execution alone is not a
promise that this separate customer-selected data flow stays local.

Artifact narratives and charts preserve source checkpoints, query/window,
quality, attribution, and exact-plan references. They never become a second
source of truth or authorization for a write. The interface, artifact editing,
and human review rules are in
[`lifecycle-contract.md`](lifecycle-contract.md#agent-facing-interface-and-human-artifacts).

Every query produces a versioned `ReportEnvelope`:

```text
schema_version
report_id
provider
source_account_ref
query_contract_hash
window_start
window_end
source_timezone
report_timezone
currency
attribution_model
attribution_window
observed_at
data_fresh_through
data_quality_statuses[]
provider_api_version
connector_version
source_ledger_checkpoints[]
```

Each `source_ledger_checkpoint` contains a stream ID, high-watermark sequence,
and head digest captured before the report is assembled. It identifies the
already-existing history used as an input; it never claims the head that will
result from appending this report. The enclosing `PERFORMANCE_OBSERVATION`
record supplies its own post-append record ID, sequence, and digest, while an
export manifest records final projection checkpoints.

It contains aggregate `PerformanceRow` records at the finest level the exact
query supports. The hierarchy is explicit so campaign, ad group/ad set, ad,
creative, keyword/search term, placement, targeting segment, and conversion
action evidence can support promised audits and recommendations without
pretending every provider supports every level.

```text
report_id
resource_level
resource_type
resource_ref
parent_resource_ref
campaign_ref
campaign_join_key
creative_family_id
creative_version_id
served_rendition_id
creative_deployment_id
resource_name
resource_status
objective
budget_type
budget_minor
spend_cap_minor
bid_strategy
bid_amount_minor
target_amount_minor
schedule_start
schedule_end
dimension_type
dimension_value
impressions
clicks
spend_minor
reach
video_views
engagements
provider_reported_results
join_status
data_quality_statuses[]
provider_extensions
```

Allowed `resource_level` values are `ACCOUNT`, `CAMPAIGN`, `AD_GROUP`, `AD`,
`CREATIVE`, `KEYWORD`, `SEARCH_TERM`, `PLACEMENT`, `TARGET_SEGMENT`, and
`CONVERSION_ACTION`. A provider may return a supported subset; absence is
explicit capability metadata, not an empty row. `dimension_type` and
`dimension_value` are typed, provider-safe breakdowns such as device, placement,
keyword match type, or approved aggregate target category. Free-form or person-
level audience values are prohibited.

Conversion data uses separate `ConversionBreakdownRow` records rather than one
ambiguous conversion total:

```text
report_id
campaign_ref
campaign_join_key
resource_ref
conversion_source
conversion_action_ref
conversion_contract_version_ref
conversion_mapping_version_ref
conversion_name
conversion_kind
counting_method
attribution_model
attribution_window
conversion_count
conversion_value_minor
currency
join_status
data_quality_statuses[]
provider_extensions
```

`conversion_source` distinguishes provider-reported, GA4 key-event, and configured
CRM-attributed aggregates. `conversion_kind` distinguishes actions such as lead,
qualified lead, purchase/revenue, install, or a provider-native outcome without
claiming they are equivalent. Conversion references become opaque in exports;
names must pass the sensitive-data classifier. A native conversion mapping
retains its own resource, source signal, counting, attribution, and verification
semantics; it does not inherit success from a GA4 key event. Mapping verification
uses separate configuration, browser, native-receipt, processed-reporting, and
optimization-association dimensions defined in
[`conversion-integrations.md`](conversion-integrations.md).

CRM-specific qualified/won counts and attributed pipeline/revenue amounts use
the fixed normalized aggregate in [`attribution-sources.md`](attribution-sources.md).
They carry the same report envelope, source checkpoint, attribution model,
window, currency, and join status. Minimum-cell suppression is enforced in the
source before retrieval. Missing outcomes remain null with a quality/capability
status; campaign traffic is never substituted for qualified pipeline. No person
or deal-level rows are a supported reporting grain.

Creative identifiers are populated only when an effective-dated deployment
proves which exact version served during the metric window. The uniform
components, colors, visual fingerprint, experiment, and deployment schemas are
defined in [`creative-intelligence.md`](creative-intelligence.md). A window that
cannot be split across two versions receives `MIXED_CREATIVE_VERSION` rather
than being attributed to the current creative.

`served_rendition_id` is nullable and is populated only when the provider proves
delivery/performance at that exact rendition or card grain. A multi-rendition,
carousel, responsive, or dynamic ad-level row keeps it null and carries
`CREATIVE_NOT_EXPOSED` or `COMBINATION_UNKNOWN` as applicable. Never emit one
copy of the same ad-level spend, impressions, clicks, or conversions for each
eligible rendition. Parent and child rollups are alternative grains and are not
summed together; mutually exclusive provider partitions must reconcile to their
declared parent tolerance, while non-additive exposure metrics are labeled.

Rules:

- Money uses integer minor units plus ISO currency, never floating point.
- When a reviewed provider delivery amount has finer precision, its namespaced
  extension retains the exact native decimal and declares the cent-projection
  rounding rule. Audits and aggregates use that retained value before any final
  display rounding.
- Time instants are ISO 8601/UTC; reports retain the source account/property
  timezone and date boundary used to query them.
- `null` means unavailable or inapplicable. It is not silently replaced by zero.
- Counts and money from incompatible attribution models remain separate rows;
  they are not summed into "true conversions."
- Provider account and resource identifiers become locally keyed opaque
  references in exported evidence. The local operator UI may show approved
  identifiers needed for account safety.
- `query_contract_hash` plus each canonical row digest covers the validated
  normalized aggregate and query contract, not a raw or rejected response.
- Provider extensions are namespaced, typed, allowlisted, and schema-versioned.
  Unknown response fields fail validation before display or persistence.

## Read-only 0.1.1 additions

Google Ads reports add two distinct aggregate conversion kinds:
`GOOGLE_ADS_CONVERSIONS` and `GOOGLE_ADS_ALL_CONVERSIONS`. These are overlapping
alternatives, never additive partitions. Conversion row schema version 2 adds the nullable
`conversion_count_decimal` field carries a canonical nonnegative decimal string
(up to 18 decimal places). Integer-compatible counts retain `conversion_count`;
fractional counts leave that legacy integer field null. An absent decimal field
is omitted when serializing legacy records, preserving their original shape.
The Google parser reads JSON decimals directly, without a binary-float round trip.
Both v1 and v2 rows remain readable; an explicit upcaster can produce a v2 view
without changing the original record. AdHelm 0.1.0 cannot read v2 rows: upgrade
the reader or use the deterministic CSV projection when sharing with that build.

The closed conversion extensions are `google_ads_date`,
`google_ads_conversion_value`, and `google_ads_rounding`. Native decimal values
remain exact, with `HALF_EVEN_TO_MINOR` disclosed for the money projection.
Action references, counting methods, and attribution settings are not invented
for these campaign/ad aggregates. Missing metrics stay unavailable, including
when the provider omits every conversion field. Old JSONL is never rewritten.

A Google Ads query may explicitly request `include_campaign_names`. The screened
`google_ads_campaign_name` extension is then displayed for that read. A later
`report show` needs `--include-campaign-names` to display it again. Default
exports and artifacts pseudonymize this field even when other marketing text
is included. The name is a label on the provider ID, never a join key.

## Join contract

Preferred joins, in order:

1. an advertising-platform campaign ID carried in an approved controlled field;
2. a stable opaque `campaign_join_key` carried in a controlled UTM or approved
   external-ID field; and
3. an explicitly configured mapping table with provenance.

Name-only, fuzzy, or inferred joins are never automatic authoritative joins.

| Join status | Meaning |
| --- | --- |
| `EXACT_PROVIDER_ID` | Approved provider campaign identifier matched |
| `EXACT_CONTROLLED_KEY` | Stable controlled campaign key matched |
| `EXPLICIT_MAPPING` | User-approved mapping with provenance matched |
| `HEURISTIC` | Candidate name/time-based match; excluded from authoritative totals |
| `UNMAPPED` | No acceptable match |
| `CONFLICT` | More than one candidate or contradictory identity |

GA4, each ad provider, and each configured CRM aggregate are presented side by side.
The report labels source, window, and attribution semantics. It does not infer
causality or incrementality.

## Data-quality statuses

Statuses are additive and visible at row/report level:

- `COMPLETE`
- `PROCESSING_PENDING`
- `PARTIAL_PAGE_FAILURE`
- `STALE`
- `SAMPLED`
- `THRESHOLDED`
- `MISSING_EVENT`
- `DUPLICATE_FIRING`
- `TIMEZONE_MISMATCH`
- `CURRENCY_MISMATCH`
- `ATTRIBUTION_MISMATCH`
- `UNMAPPED`
- `AMBIGUOUS_REMOTE_STATE`
- `PROVIDER_REPORTED_UNKNOWN`
- `MIXED_CREATIVE_VERSION`
- `CREATIVE_NOT_EXPOSED`
- `COMBINATION_UNKNOWN`
- `CREATIVE_METADATA_MISSING`
- `EXTRACTION_FAILED`
- `MINIMUM_CELL_SUPPRESSED`
- `SOURCE_EDITION_UNAVAILABLE`
- `NOT_AVAILABLE_FROM_PROVIDER`
- `NOT_SUPPORTED_BY_ANALYZER`

Only `COMPLETE` means no known caveat for the declared query. Provider downtime,
thresholding, processing delay, and missing data are never reported as healthy
zero performance.

## Creative analysis rules

- Join performance through `CreativeDeployment` intervals, never merely the
  provider's current ad/creative ID.
- Group by family, version, component, palette/color, visual/execution feature,
  CTA, or experiment only when the relevant creative record and performance
  granularity are available.
- Preserve exact platform-copy roles and normalized roles together.
- Split performance at version boundaries when source granularity permits it;
  otherwise label it `MIXED_CREATIVE_VERSION` and exclude it from a single-
  version conclusion.
- Responsive-search and dynamic-creative component performance is reported only
  when the provider exposes component/combination delivery at that granularity.
  Ad-level results cannot rank a particular headline, CTA, color, or combination.
- Multi-rendition/carousel ad metrics remain at ad grain unless the provider
  returns exact rendition/card rows. The report never fans one metric row out
  across eligible assets or sums parent and child rollups together.
- Cross-platform comparisons are directional and expose differences in format,
  audience, placement, delivery optimization, and attribution.
- Analyzer/extractor schema and version are dimensions. Do not silently compare
  a palette or OCR result produced by materially different algorithms.

## Audit finding

```text
finding_id
finding_type
severity
provider
resource_refs[]
observation
evidence_refs[]
data_window
confidence
risk
suggested_action
automatic_write_allowed = false
```

A finding is reproducible from normalized evidence or a redacted configuration
digest. It never embeds secrets, person-level data, raw request/response bodies,
custom-code source, cookies, or URL/query values.

## Recommendation record

This typed result is available without a presentation file. Rendering it as a
document, spreadsheet, or HTML view follows the user's output preferences.

```text
recommendation_id
hypothesis
evidence_refs[]
observations[]
assumptions[]
confidence
expected_impact
risk
spend_impact_minor
currency
proposed_plan_ref
expires_at
```

Recommendations must distinguish observation from inference. Expected impact is
a bounded estimate or directional statement with its method, not a guarantee.
No recommendation can mutate remote state; it becomes actionable only through a
new immutable plan and exact authorization, either directly from the user or
under their explicit bounded delegation policy. See
[`authorization-policy.md`](authorization-policy.md). A model claim or report
artifact alone is never authority to execute.

## Evidence envelope

An exported evidence record may contain:

- schema/tool/connector/API/policy versions;
- source, query dimensions, date window, timezone, currency, and attribution
  context;
- opaque local account/resource references;
- sanitized normalized aggregates and their digests;
- plan, authorization-decision, before/after, version, dependency-graph, and result digests;
- source JSONL stream IDs, high-watermark sequences, and head digests;
- actor identity local to the customer's environment;
- timestamps, outcome/status, endpoint domains, and recovery state; and
- references to local validation artifacts the user chose to retain.

It may not contain:

- credentials, authorization codes, token material, secrets, or process
  arguments;
- raw API responses, request bodies, cookies, headers, or query values;
- names, emails, phones, CRM/customer/account-holder IDs, raw click IDs, or
  person-level rows;
- DOM/page text, entered form values, sensitive URLs/data-layer values, or
  custom HTML, custom-template, or other custom-code source; or
- audience files, PHI, financial traits, eligibility/underwriting data, or
  enhanced-conversion `user_data`.

Before sharing, the CLI shows an inventory and redaction summary and requires an
explicit export destination. Support bundles use the same envelope and are
never uploaded automatically.

The deterministic CSV bundle and its formula-injection, encoding, ordering,
manifest, and integrity rules are defined in
[`local-ledger-and-exports.md`](local-ledger-and-exports.md). CSV always derives
from verified JSONL; there is no dual-write path.
